An agent can propose a payment. It cannot authorise one.

cancho-chain makes the authority granted to an autonomous agent that moves assets explicit, bounded, enforceable and auditable: a typed intent, a policy decision outside the model, and the exact transaction bytes read back before anything is signed. Pure cancho, each piece checked against libraries and separate models, then against itself broken on purpose.

See a decisionSee the evidence

The agent's output is data

The intent is one JSON object checked against a strict schema. Unknown keys, duplicate keys, escapes, floats written as integers and non-canonical amounts are refused, and an accepted intent has one canonical form and one digest however it was spelled.

Authority is decided outside the model

The policy engine is a pure function of a policy, the intent, the authenticated caller, the time, the registry and the history. It answers allow, refuse or approval-required, with one of fourteen stable reasons, and a record bound to the intent, the policy version and the time window.

The bytes are read back

A strict RLP decoder, sharing no code with the encoder, reads the exact transaction that is about to be signed and refuses unless every field is what was authorised: chain, nonce, token, recipient, amount, fee and gas caps.

A refusal is a success

Each refusal has a stable code and a reason. Nothing falls through to "allowed": a missing registry answer, an expired policy, a replayed request or a malformed input all fail closed, and the test for each is written first.

Held to oracles, and to mutants

Every slice is compared with an independent implementation (eth-account, libsecp256k1, rlp, jsonschema) and then with itself broken on purpose: each deliberate fault must be caught, or be explained as unreachable.

Honest about what is missing

There is no signing process, no RPC, no evidence log and no independent review yet. Constant time of the signing code is a design claim, not a measurement. The list is part of the page.

How it works.

The agent is untrusted: its output is data, never authority. Each step has its own check, and the signer, when it exists, will be a separate process that holds the key and the only authority to sign.

Look at one decision.

The policy of the proposal's example: one asset on one test network, two approved suppliers, 500 USDC per transaction, 2,000 a day, a human above 250. Amounts are integers of base units (USDC has six decimals). The same intent, six amounts, run through the compiled engine.

# policy: per_transaction 500000000, daily_total 2000000000, approval_required_above 250000000
amount       outcome            reason
100000000    allow              ALLOWED
250000000    allow              ALLOWED                  # at the threshold, not above it
250000001    approval required  APPROVAL_REQUIRED        # within every limit; a human decides
500000000    approval required  APPROVAL_REQUIRED
500000001    refuse             AMOUNT_LIMIT_EXCEEDED    # one base unit over the per-transaction limit
# the same intent, but...
refuse  PRINCIPAL_MISMATCH   # the authenticated caller is not the policy's principal
refuse  POLICY_REVOKED       # the registry says so
refuse  POLICY_EXPIRED       # now == not_after: the window is half-open

These are outputs of the compiled decision function, not an illustration. The first check that fails answers, in a fixed order (registry, validity window, caller, operation, chain, asset, recipient, per-transaction limit, replay, daily total, approval), and a test builds every combination of up to three of the fourteen reasons to hold that order.

Why the agent cannot talk its way round it

The engine has no operation that changes a policy, an allowlist or a key, so there is no flag to set false and no argument to send. The agent only ever supplies an intent.

Why a retry cannot pay twice

The engine is given the history of authorisations already issued. The same intent digest in it is REQUEST_REPLAYED: reconcile, do not ask again. The daily window is a rolling 86,400 seconds and counts what was issued, not only what settled.

Why the digest matters

The decision record carries the intent digest, the policy digest, the caller and the time window, and has its own digest. It cannot be presented for another intent, another policy version, or after it expires.

What it does not do, and what is not built.

Not built yet

  • Anything against a real chain: the executor has only met mock nodes, speaks plain HTTP (no TLS, no chunked answers) and does not verify the signature.
  • The signer's anchor (the ledger's count and head, kept outside it), and constant-time secp256k1.
  • An independent review of the signer, the executor and the policy.
  • A policy registry and an evidence-backed history (the engine is given their answers).

Never claimed

  • That an invoice is genuine, a supplier legitimate or a policy wise.
  • That a token is safe or an approved contract has no bug.
  • That an RPC provider is honest, or that a transfer can be reversed.
  • That an application is secure because it uses cancho.

Open, and stated

  • Constant time of secp256k1 signing: not measured (cancho#712).
  • One transaction shape: an ERC-20 transfer in EIP-1559 form, on one network.
  • The Python models were written from the same specification as the code; the independent checks are the libraries named above.
  • Nothing has been independently reviewed.

Status: research

  • Built and checked: the typed intent, the policy and its decision, the strict decoder and the final-transaction validator, the encoders, Keccak-256 and (in the cancho repository) secp256k1 signing. The code is a draft pull request, #1.
  • Dependencies are consumed from sibling checkouts until secp256k1 and cancho-schema are published to a store at a pinned commit.
  • The design is docs/design.md: every claim in it is marked measured, read, a choice, or open, and a claim found false is corrected in place (it has happened: the address rule of section 8.1 was wrong and is corrected where it was made).

Try it.

The checks need the cancho compiler built from source (stage 2 of scripts/build-standalone.sh), a sibling checkout of cancho and cancho-schema, and a few Python packages.

git clone https://github.com/alpibrusl/cancho-chain && cd cancho-chain
pip install eth-account coincurve jsonschema pycryptodome
export CANCHO=/path/to/cancho CANCHO_PACKAGES=../cancho/packages CANCHO_SCHEMA=../cancho-schema/src/schema.cho

cancho build --bin chain
python3 -I scripts/check_keccak.py [--mutants]     # Keccak-256
python3 -I scripts/check_eth.py    [--mutants]     # addresses, RLP, ERC-20, type-2 transactions
python3 -I scripts/check_decode.py [--mutants]     # strict decoder and final validator
python3 -I scripts/check_intent.py [--mutants]     # the typed intent
python3 -I scripts/check_policy.py [--mutants]     # the policy and the decision
